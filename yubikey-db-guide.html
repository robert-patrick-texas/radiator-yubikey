A how-to guide for offline YubiKey one-time-password (OTP) logins on Radiator RADIUS, with the YubiKeys kept in a local SQLite database or a shared PostgreSQL database, managed with the scripts in this repository. It covers a lab you can build in a container, a server installation, adding accounts, checking credentials, day-to-day maintenance, moving from SQLite to PostgreSQL, a second PostgreSQL server that takes over when the first fails, three sites with automatic failover, logins at a site that is cut off, one anycast address for all of them, and a tool that sets up all of that from one input file.

The scripts, this guide and the releases are on GitHub, under the MIT license: https://github.com/robert-patrick-texas/radiator-yubikey.

Every procedure in this guide was run as written with Radiator 4.30 on Ubuntu 26.04 LTS with PostgreSQL 18 (and Ubuntu's Patroni 4.1 and etcd 3.5 for three sites, and FRR 10.5 for anycast), and tests/radiator/run.sh repeats the checks (see Testing).

How it works

Each time someone touches a YubiKey, it types a 44-character OTP. The first 12 characters are the YubiKey's public ID. The other 32 are a token encrypted with an AES key stored in the YubiKey. The token holds the YubiKey's private ID and two counters that go up with every OTP.

Radiator's <AuthBy SQLYUBIKEY> checks a login like this:

  1. It splits what the user typed into the static password (PIN), the public ID and the token. Both 1234:vvccccbbcdef... and 1234vvccccbbcdef... work.
  2. It looks up the row for that username and public ID in the database.
  3. It decrypts the token with the AES key from that row and checks its CRC.
  4. It checks that the private ID in the token matches the row (CheckSecretId).
  5. It rejects the OTP unless its counters are ahead of the ones saved in the row, so a captured OTP can't be used twice, and then saves the new counters. The database refuses to save counters that don't move forward, so even the same OTP sent to two Radiator servers at the same moment is accepted only once.

Nothing is sent to Yubico. The catch is that Radiator must know each YubiKey's AES key, and Yubico keeps the factory key secret, so every YubiKey is reprogrammed with an AES key you generate, and that key is loaded into the database.

SQLite or PostgreSQL?

SQLite PostgreSQL
Where the keys are One file on the Radiator server A database that several Radiator servers can share
Several Radiator servers Each has its own file and its own counters, so an OTP used on one server is still accepted on another One set of counters, so an OTP works only once anywhere
Who can change what Anyone who can write the file Radiator's login can read keys and update only counters; admins are members of an admin role
To run Nothing more A PostgreSQL 18 server, on the Radiator server or elsewhere (over TLS)
If the database server fails — A second server can take over (see Two database servers), or with three sites, Patroni moves the primary by itself (see Three sites)

Start with SQLite for one Radiator server. Use PostgreSQL when more than one Radiator server checks the same YubiKeys. You can move later (see Move from SQLite to PostgreSQL).

Try it in a lab container

A lab shows the whole setup working before you touch a server, and needs no YubiKey: tests/make-otp.sh makes OTPs for test keys. The container is Ubuntu 26.04 with Radiator, SQLite and PostgreSQL 18 (and Patroni and etcd, which only the three-site test uses).

Build the lab image

Put the two Radiator packages in a directory of their own, then build the image from the repository's tests/radiator/Dockerfile:

git clone https://github.com/robert-patrick-texas/radiator-yubikey.git
cd radiator-yubikey
mkdir -p ~/radiator-packages        # copy radiator_*.deb and radiator-radius-utilxs_*.deb here
docker build -t radiator-yubikey-lab -f tests/radiator/Dockerfile ~/radiator-packages

Start a container with the repository mounted read-only at /opt/radiator-yubikey, where the package puts the scripts on a server. You work as root inside it, so the commands below have no sudo:

docker run -it --rm --name yk-lab -v "$PWD:/opt/radiator-yubikey:ro" -w /opt/radiator-yubikey radiator-yubikey-lab bash

SQLite in the lab

Create the database, add a test user, and install the Radiator configuration (sections 6 to 8 explain each step):

./yubikey-db.sh init --owner radiator:radiator
./yubikey-db.sh add -u alice -P vvccccbbcdef -p 4a6f8e2d1c3b -k 6b1f0a9d2c7e4f3a8b5d0c1e9f2a7b6d -w 1234
./yubikey-db.sh config > /etc/radiator/conf.d/yubikey.conf
install -m 0640 -o root -g radiator radiator.example.conf /etc/radiator/radiator.conf

Start Radiator as the radiator user, the way its systemd unit does:

sudo -u radiator /opt/radiator/radiator/radiusd -foreground -no_pid_file -config_file /etc/radiator/radiator.conf &
sleep 2

Log in with an OTP for alice's test key (counter 1), then try the same OTP again:

OTP=$(tests/make-otp.sh vvccccbbcdef 4a6f8e2d1c3b 6b1f0a9d2c7e4f3a8b5d0c1e9f2a7b6d 1)
/opt/radiator/radiator/radpwtst -s 127.0.0.1 -secret local-test-secret -auth_port 1812 -noacct -user alice -password "1234:$OTP"
/opt/radiator/radiator/radpwtst -s 127.0.0.1 -secret local-test-secret -auth_port 1812 -noacct -user alice -password "1234:$OTP"
tail -2 /var/log/radiator/authentication.log

The first login prints OK; the second prints Rejected: Request Denied, and the log gives the reason, Replay attack detected. Check the next OTP without Radiator, and look at the saved counters:

printf '%s\n' 1234 "$(tests/make-otp.sh vvccccbbcdef 4a6f8e2d1c3b 6b1f0a9d2c7e4f3a8b5d0c1e9f2a7b6d 2)" | ./yubikey-db.sh verify -u alice
./yubikey-db.sh list

PostgreSQL in the lab

Start PostgreSQL, create its roles and database (root is the lab's admin), copy alice over from SQLite, and point Radiator at PostgreSQL:

pg_ctlcluster 18 main start
sudo -u postgres ./yubikey-db.sh -b pg init-pg --admin root
./yubikey-db-migrate.sh /etc/radiator/db/yubicred.db
./yubikey-db.sh -b pg config > /etc/radiator/conf.d/yubikey.conf
pkill -f radiusd; sleep 1
sudo -u radiator /opt/radiator/radiator/radiusd -foreground -no_pid_file -config_file /etc/radiator/radiator.conf &
sleep 2

The counters came along, so the OTP that verify used (counter 2) is rejected, and the next one is accepted:

for n in 2 3; do
    /opt/radiator/radiator/radpwtst -s 127.0.0.1 -secret local-test-secret -auth_port 1812 -noacct -user alice \
        -password "1234:$(tests/make-otp.sh vvccccbbcdef 4a6f8e2d1c3b 6b1f0a9d2c7e4f3a8b5d0c1e9f2a7b6d $n)"
done
./yubikey-db.sh -b pg list

With a real YubiKey

Program a spare YubiKey as in Program the YubiKeys, add it (the script asks for the private ID, AES key and PIN), then touch the YubiKey when asked:

./yubikey-db.sh -b pg add -u you -P <public ID from ykman>
./yubikey-db.sh -b pg verify -u you

For a login through Radiator, read the OTP into a variable first, because the YubiKey presses Enter after the OTP:

read -rsp 'PIN: ' PIN; echo; read -rp 'Touch the YubiKey: ' OTP
/opt/radiator/radiator/radpwtst -s 127.0.0.1 -secret local-test-secret -auth_port 1812 -noacct -user you -password "$PIN:$OTP"

Leave the container with exit; --rm deletes it.

The automated test

tests/radiator/run.sh builds the same image, with Patroni, etcd and FRR (and debhelper and lintian, to build and check the package) added, and runs six tests of real Radiator logins:

  • e2e.sh, 145 checks in a throwaway container: SQLite with and without Require2Factor, PostgreSQL over the local socket and over TLS, the example wrapper, a user with two YubiKeys (each with its own counters, PIN and active; another user's YubiKey refused), a cutover from SQLite to PostgreSQL while Radiator runs, the same OTP sent twice at the same moment to two of Radiator's farm processes (accepted twice without the trigger, once with it), and a counter save on PostgreSQL whose answer is lost (its session ended while it waits for a standby: not answered with 1.8.1's UpdateQuery, accepted with this one's), and a YubiKey stored for the username DEFAULT, which logs in no one else, and the anycast check renewing its key with Radiator's login over TLS, then logging in with the new key (Radiator refuses the old one). For each login it checks Radiator's answer and the reason it logs, and that verify agrees.
  • groups.sh, 133 checks in a throwaway container, with radiator-groups.example.conf and devices at addresses in 127.0.0.0/8: logins over TACACS+ (with a small client on Radiator's own modules, and with Radiator's tacacsplustest) and RADIUS, by YubiKey and by service account, from devices in three device groups and from an unlisted one, on SQLite and then PostgreSQL. It checks each login, privilege level, command authorization and RADIUS reply against the groups; a login followed by eight authorizations at once, which several of Radiator's processes answer; enable; accounting; that a change in the groups, or a disabled account, applies to a session already open; and that nothing is allowed while PostgreSQL is stopped. It also runs the anycast check's check over RADIUS and TACACS+, set up as in Set up anycast on each server, step 5, with its service account disabled, its group's access taken away, another password in the database, a wrong key, a wrong port and an address Radiator doesn't listen on; and that its accounts can't log in from a device.
  • ha.sh, 63 checks with four containers: two PostgreSQL servers (primary and streaming standby, over TLS) and two Radiator servers, through a dead primary, a hung primary, failovers, an old primary coming back, a planned switchover (a login held until the standby is promoted, and one held for 5 s, then rejected, when none is), the replay window (see Two database servers), and the same OTP sent to both Radiator servers at the same moment.
  • geo.sh, 212 checks with three containers, one per site, each running systemd with etcd, PostgreSQL under Patroni, Radiator, FRR and yubikey-anycast.sh from the package, set up as in Three sites and Anycast, with traffic control adding the WAN delays (55 ms between West and East, 4 ms between the East sites). A fourth container stands in for West's router (FRR), and a fifth, behind it, is a RADIUS client that logs in at the anycast addresses, over IPv4 and IPv6. It measures login times, switches the primary over twice while four users at each site log in at the same time, then stops West's Radiator and West's check, reboots each server in turn, cuts West's and then the primary's power, kills Patroni on the primary, cuts West off, cuts the primary's site off, breaks the link between the East sites, copies a standby again, and takes two servers down at once. Then it sets up partition mode, has West's check renew its key under systemd (and West's copy get it), and cuts West off, cuts the primary's site off, takes two servers down at once, and breaks the link between the East sites again. Each time it checks which logins are accepted, which OTPs are replays, that the cluster recovers, which servers the router has anycast routes from, and which server answers the client. Last, it sets up the automatic backups with the guide's steps (the key pair made on the client, as the admins' machine), checks and decrypts one there, and restores it on the primary, at its prompt, after a login: the OTP stays used, and the sites go on logging users in and advertising. The containers have the SYS_ADMIN capability (for systemd) and NET_ADMIN (for traffic control and addresses in their own network), but aren't privileged. Docker sets the two kernel settings of Set up anycast on each server, step 2, in the containers (--sysctl); the step's commands themselves were run in a container whose kernel settings it could change for its own network only.
  • package.sh, 49 checks of the package and install.sh: the package builds the same twice, lintian finds nothing in it, and it puts nothing outside /opt/radiator-yubikey but its units. Then, on fresh Ubuntu 26.04 containers (apt-get in them needs network access): without Radiator, where install.sh stops, or goes on with --yes; with Radiator Software's packages; with Radiator's source unpacked in /opt/radiator/radiator; and with it installed with make install (taken from the radiator package, which holds Radiator's source distribution). Each Radiator then accepts a login and rejects the same OTP again. Last, under systemd: units installed by hand as this guide said before the package, replaced with install.sh's commands; the package's units (and the backups' timer) neither enabled nor started by the install, and found sound by systemd-analyze verify, restarted by an upgrade only while they run, stopped by a removal, and gone after a purge.
  • turnkey.sh, 155 checks of the turn-key setup: yubikey-turnkey makes the folders from a site.toml with two routers at West's site, and setup.sh runs on three fresh Ubuntu 26.04 containers (systemd and iproute2 only) at the same time, installing everything with apt-get (it needs network access). Two more containers are the routers (FRR), and one behind them is a device, and the admins' machine. It checks the tool's output, --check on a fresh server, the cluster, the anycast checks, both routers' routes and BFD sessions; logins at the anycast addresses over RADIUS and TACACS+, IPv4 and IPv6, by YubiKey and by service account, refused for a group without access to the device's group and from an unlisted device (the catch-all) until its group has access; West withdrawn from both of its routers when only its TACACS+ login fails, and when its check stops; setup.sh --status (OK on all three, also without the folder; and what it says with etcd stopped on one server, a router down, the primary moved, West withdrawn, and a folder copied but not set up); the backups (the first, made by setup.sh, more on a standby, how many it keeps, --status with one 30 hours old and with the timer stopped; one checked and decrypted on the admins' machine, with a key pair made as this guide says, and restored on the primary after a login, a deleted YubiKey, a group change and a renewed anycast key: what it undoes, the counters and keys it keeps, logins right after, and no restore on a standby); the firewall (PostgreSQL closed to a machine outside the admin subnets, Patroni's REST API open to the admins); setup.sh run again (nothing installed or restarted); a reboot; a new device added in site.toml; new certificates, one server at a time (etcd, Patroni and PostgreSQL present them); and --reset on all three, then setup.sh again, and the last backup restored into the new cluster.

Install on the servers

Radiator server

Install Radiator first. It comes from Radiator Software, as packages or as source, and the scripts work with either.

Radiator Software's packages, as this guide uses:

sudo apt install ./radiator_4.30-1_all.deb ./radiator-radius-utilxs_2.4-4.resolute_amd64.deb

The package creates the radiator user, installs Radiator in /opt/radiator/radiator (its tools, such as radpwtst, aren't on the PATH), and adds the radiator.service systemd unit, which runs Radiator as radiator with /etc/radiator/radiator.conf.

Radiator's source: unpacked in /opt/radiator/radiator, where the systemd unit in its goodies directory runs it, or installed with perl Makefile.PL && make && sudo make install (as its Makefile.PL says), which puts radiusd and radpwtst in /usr/local/bin. Then make what the package would have made: the radiator user, Radiator's directories, and the systemd unit (for a make install, with its /opt/radiator/radiator paths changed to where radiusd is):

sudo groupadd -r radiator
sudo useradd -r -g radiator -d /var/lib/radiator -s /usr/sbin/nologin radiator
sudo install -d /etc/radiator/conf.d
sudo install -d -o radiator -g radiator /var/log/radiator /var/lib/radiator
sudo install -m 0644 goodies/radiator.service /etc/systemd/system/   # in the source directory

Where this guide runs /opt/radiator/radiator/radiusd or radpwtst, run yours. After a make install, give radpwtst the source's dictionary (-dictionary /usr/src/radiator/dictionary, for example), and in Install the configuration, set DictionaryFile to it too.

The radiator-yubikey package

The scripts come as a package, radiator-yubikey, which puts them in /opt/radiator-yubikey, and install.sh, which installs the package with the packages that it and Radiator's YubiKey support need. Download both from a release into one directory, and run install.sh there:

rel=https://github.com/robert-patrick-texas/radiator-yubikey/releases
v=$(curl -fsSLI -o /dev/null -w '%{url_effective}' $rel/latest); v=${v##*/v}   # the latest version
curl -fLO $rel/download/v$v/radiator-yubikey_${v}_all.deb
curl -fLO $rel/download/v$v/install.sh
sudo bash install.sh

The second line finds the latest release's version, such as 1.8.0; for another release, set v to its version instead.

install.sh:

  1. Looks for Radiator: Radiator Software's radiator (or radiator-locked) package, or a radiusd from their source with Radiator's Perl modules, in /opt/radiator/radiator or on the PATH (give another one with --radiusd FILE). Radiator isn't a dependency of the package, so that either kind works. When it finds neither, it says how to install Radiator, and asks whether to go on without it; with no terminal to ask on, it stops (exit status 3), unless you give --yes. Without Radiator, the scripts still manage a database, for example on a server that only holds the database.
  2. Installs with apt-get: libauth-yubikey-decrypter-perl and libcrypt-rijndael-perl (Radiator's YubiKey support), libcache-fastmmap-perl (for DupCache shared in radiator.example.conf), libdbd-sqlite3-perl, sqlite3, libdbd-pg-perl, postgresql-client, and the package. Checks that Radiator's Perl loads Radiator's SQLYUBIKEY module and the modules it needs, and lists what is left to do: for Radiator from source, a missing radiator user or radiator.service; for units installed by an earlier version of this guide, how to use the package's instead (see After upgrading the scripts).

The package puts the scripts, their examples, tests/make-otp.sh, this guide (yubikey-db-guide.html), the README and the changelog in /opt/radiator-yubikey. It also installs the systemd units yubikey-partition.service and yubikey-anycast.service, for Partition mode and Anycast, and yubikey-backup.service with yubikey-backup.timer, for Automatic backups, but enables and starts none of them.

The examples in this guide run from /opt/radiator-yubikey (cd /opt/radiator-yubikey). With SQLite, run the scripts with sudo, because the database belongs to radiator. With PostgreSQL, run them as yourself, as a member of the admin role (set up in Create the database); export DB_BACKEND=pg in your ~/.profile saves typing -b pg every time.

To upgrade, run the new release's install.sh with its package, the same way, then see After upgrading the scripts. The services that run (yubikey-partition, yubikey-anycast) restart with the new scripts; one that you stopped stays stopped. While yubikey-anycast restarts, the server's anycast addresses are off lo for 5 to 10 s, and the routers send RADIUS to another site.

To remove the scripts, sudo apt remove radiator-yubikey: it stops the two services and removes /opt/radiator-yubikey. The database, and Radiator's configuration and the settings in /etc/radiator, stay.

Without the package, clone the repository to the same place; its install.sh then installs the other packages only:

sudo git clone https://github.com/robert-patrick-texas/radiator-yubikey.git /opt/radiator-yubikey
cd /opt/radiator-yubikey
sudo ./install.sh

For partition mode, anycast and the backups, install their units yourself: sudo install -m 0644 yubikey-partition.service yubikey-anycast.service yubikey-backup.service yubikey-backup.timer /etc/systemd/system/, then sudo systemctl daemon-reload. To build the package from a clone, see packaging/build-deb.sh.

Program the YubiKeys

Do this once for each YubiKey, on a trusted workstation. The command overwrites OTP slot 2, which types an OTP on a long touch (slot 1 is the short touch).

Warning

Slot 1's factory configuration can't be restored. After you reprogram it, the key no longer works with services that check OTPs through YubiCloud. Use slot 2 unless you're sure.

ykman otp yubico 2 --serial-public-id --generate-private-id --generate-key

ykman shows three values. Record them for this user:

ykman output yubikey-db.sh option CSV column Format
Public ID -P public_id 12 modhex characters (only cbdefghijklnrtuv)
Private ID -p private_id 12 hex characters
Secret key -k aes_key 32 hex characters

If a user gets more than one YubiKey, also note which is which, and the slot, for example primary, slot 2 and spare, slot 2: store that as the YubiKey's label (-l, or the CSV column label), which list shows.

Caution

Do not add --upload: it sends the key to Yubico.

To choose the public ID yourself, replace --serial-public-id with --public-id <12 modhex characters>. Radiator accepts only 12-character public IDs.

Create the database

SQLite

sudo ./yubikey-db.sh init --owner radiator:radiator

This creates /etc/radiator/db/yubicred.db (use -d FILE for another path). Radiator writes to the database after every login, and SQLite writes a journal file next to it, so --owner gives the radiator user the file and its folder. init is safe to run again.

PostgreSQL on the Radiator server

Create the roles and the database as the postgres superuser, and make yourself an admin:

sudo -u postgres ./yubikey-db.sh -b pg init-pg --admin "$USER"

This creates:

  • the database yubikey (-d NAME for another name), with the yubikeys table;
  • the role yubikey_admin, which owns them; --admin LOGIN makes a login a member, and you can repeat it;
  • the role radiator, Radiator's login. It can read the lookup columns and update only the counters and the access time.

Radiator connects over the local socket, where Ubuntu's PostgreSQL uses peer authentication: the radiator OS user logs in as the radiator role with no password. Admins log in the same way as themselves.

PostgreSQL on a separate server

Radiator then connects over the network, with TLS and a password. Below, the database server is db.example.com, the Radiator server 192.0.2.21, and the admin opsadmin works on the Radiator server.

On the database server:

  1. Install a TLS certificate for the name Radiator connects to. Use your own CA if you have one. For a lab, make a CA and a certificate:

    openssl req -x509 -newkey rsa:3072 -nodes -days 3650 -subj "/CN=YubiKey DB CA" -keyout ca.key -out ca.crt
openssl req -newkey rsa:3072 -nodes -subj "/CN=db.example.com" -addext "subjectAltName=DNS:db.example.com" \
        -keyout server.key -out server.csr
openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 825 -copy_extensions copy -out server.crt
sudo install -m 0644 -o postgres -g postgres server.crt /etc/postgresql/18/main/server.crt
sudo install -m 0600 -o postgres -g postgres server.key /etc/postgresql/18/main/server.key

    Keep ca.key offline. Radiator's server needs only ca.crt.

  2. Make PostgreSQL listen on the network with that certificate:

    sudo tee /etc/postgresql/18/main/conf.d/yubikey.conf >/dev/null <<'EOF'
listen_addresses = '*'
ssl = on
ssl_cert_file = '/etc/postgresql/18/main/server.crt'
ssl_key_file = '/etc/postgresql/18/main/server.key'
EOF

  3. Allow radiator and opsadmin from the Radiator server, over TLS only. Add these lines to /etc/postgresql/18/main/pg_hba.conf above the first line that starts with host:

    hostssl  yubikey  radiator  192.0.2.21/32  scram-sha-256
hostssl  yubikey  opsadmin  192.0.2.21/32  scram-sha-256

    Then sudo systemctl restart postgresql, and open TCP port 5432 to 192.0.2.21 in any firewall.

  4. Create the roles and the database, set Radiator's password (it asks for it), and give the admin a password:

    sudo -u postgres ./yubikey-db.sh -b pg init-pg --admin opsadmin --set-password
sudo -u postgres psql -c '\password opsadmin'

    This needs the scripts on the database server too, only for this step.

On the Radiator server, as opsadmin:

  1. Install the CA certificate where Radiator and the admins can read it:

    sudo install -m 0644 ca.crt /etc/radiator/pg-ca.crt

  2. Tell psql and the scripts where the database is, and store the password (~/.pgpass must be mode 0600):

    cat >> ~/.profile <<'EOF'
export PGHOST=db.example.com PGUSER=opsadmin PGSSLMODE=verify-full PGSSLROOTCERT=/etc/radiator/pg-ca.crt
export DB_BACKEND=pg
EOF
(umask 077; echo 'db.example.com:5432:yubikey:opsadmin:YOUR-PASSWORD' >> ~/.pgpass)
. ~/.profile
./yubikey-db.sh list

    list shows an empty table when everything works. verify-full checks that the server's certificate is for db.example.com and signed by your CA.

With these settings, ./yubikey-db.sh config writes the same connection into Radiator's configuration: host, port, sslmode=verify-full and sslrootcert, and connect_timeout=2. You add Radiator's password in the next section. For a second database server that takes over when this one fails, see Two database servers.

Configure and start Radiator

Install the configuration

The Radiator package's sample /etc/radiator/radiator.conf is for a first test only.

Caution

The sample radiator.conf accepts every login from 127.0.0.1 without a password check, and accepts requests from any client that uses the secret mysecret. If you add the YubiKey clause to it, a test with radpwtst on the server succeeds without ever reaching the database. Replace it.

Install radiator.example.conf in its place, then set your RADIUS clients:

sudo cp -p /etc/radiator/radiator.conf /etc/radiator/radiator.conf.orig
sudo install -m 0640 -o root -g radiator radiator.example.conf /etc/radiator/radiator.conf
sudoedit /etc/radiator/radiator.conf

In the editor, change the Secret of <Client 127.0.0.1> (used for tests on the server), and replace the <Client 192.0.2.10> example with one block per RADIUS client (VPN gateway, switch, wireless controller), each with its own long random secret.

radiator.example.conf runs four Radiator processes (FarmSize 4). Each answers one request at a time, so one slow database query, for example while a database server fails over, no longer holds up every other login. DupCache shared lets the processes recognize a request that a RADIUS client sent again to another process; it needs libcache-fastmmap-perl (installed above) and keeps a file of about 290 MB at /var/lib/radiator/dupcache while Radiator runs.

Write the YubiKey clause from yubikey-db.sh config to /etc/radiator/conf.d/yubikey.conf, which radiator.conf includes. Create the file first, so it is readable only by root and radiator; tee keeps that owner and mode:

sudo touch /etc/radiator/conf.d/yubikey.conf
sudo chown root:radiator /etc/radiator/conf.d/yubikey.conf
sudo chmod 0640 /etc/radiator/conf.d/yubikey.conf
./yubikey-db.sh config | sudo tee /etc/radiator/conf.d/yubikey.conf >/dev/null          # SQLite
./yubikey-db.sh -b pg config | sudo tee /etc/radiator/conf.d/yubikey.conf >/dev/null    # PostgreSQL

For PostgreSQL on a separate server, also put Radiator's password on the DBAuth lines (sudoedit /etc/radiator/conf.d/yubikey.conf): one in each clause, YubiKeySQL, ServiceAccounts and GroupAccess. This is why the file must not be readable by other users.

The clause it writes, for SQLite:

<AuthBy SQLYUBIKEY>
    Identifier   YubiKeyLocal
    DBSource     dbi:SQLite:dbname=/etc/radiator/db/yubicred.db
    DBUsername
    DBAuth
    AuthSelect   select secret, active, userId, counter, low, high, password from yubikeys where username=%0 and tokenId=%3
    UpdateQuery  update yubikeys set accessed=datetime(%5,'unixepoch'), counter=%0, low=%1, high=%2 where username=%3 and tokenId=%7
    Require2Factor
    CheckSecretId
    NoDefault
</AuthBy>
  • AuthSelect finds the row by both the username and the public ID, so a user can have several YubiKeys and one user's YubiKey can't log in as another user.
  • UpdateQuery saves the counters after each login. For PostgreSQL it uses to_timestamp(%5), because Radiator's default current_timestamp() isn't valid there, and it names the login with set_config, so that the same login may save the same counters again (see Database layout).
  • CheckSecretId checks the private ID inside the OTP against the database.
  • NoDefault: never fall back to a user called DEFAULT, as some Radiator clauses do for a user they don't find. Radiator's YubiKey clauses already don't, by default; the line keeps it so.
  • Require2Factor: see below.
  • For PostgreSQL, config also writes Timeout 2, ConnectTimeout and FailureBackoffTime 2, so Radiator gives up quickly on a database server that doesn't answer and tries again after 2 s, not 600 s, and hooks that hold a login for a few seconds while the primary changes (see Configure Radiator for two servers). The YubiKey clause is then YubiKeySQL, and YubiKeyLocal, the name the Handlers use, is a group of two clauses: YubiKeyConnect, which connects to the database first, then YubiKeySQL.

Choose: PIN and OTP, or OTP only

Require2Factor Users with a PIN Users without a PIN
Set (as config writes it) Must type PIN:OTP or PINOTP Always rejected
Removed May type just the OTP: the PIN is checked only if they type one Type just the OTP

Keep Require2Factor and give every user a PIN, unless you've decided on OTP-only logins for everyone. Without it, the PIN is optional even for users who have one. If you remove it, also use verify --no-require2factor (and require2factor=no in the example wrapper), so their checks match Radiator.

Check and start

Check the configuration as the radiator user, then look at the end of the log:

sudo -u radiator /opt/radiator/radiator/radiusd -c -foreground -no_pid_file -config_file /etc/radiator/radiator.conf
sudo tail -n 5 /var/log/radiator/radiator.log

Fix anything reported as ERR or WARNING; radiusd -c exits with 0 even then.

Important

Run radiusd checks as radiator, never as root. Run as root, it creates /var/log/radiator/radiator.log owned by root, and the service can then no longer write its log (Log could not append ... Permission denied). If that happened, sudo chown radiator:radiator /var/log/radiator/*.

Start Radiator now and at every boot, and check it's running:

sudo systemctl enable --now radiator
systemctl status radiator

After each change to the configuration, sudo systemctl restart radiator. If a firewall runs on the server, allow RADIUS from each client, for example sudo ufw allow from 192.0.2.10 to any port 1812 proto udp.

Radiator logs to /var/log/radiator/radiator.log, and each login, with the reason for a reject, to /var/log/radiator/authentication.log. Only root and radiator can read them, so use sudo to read them.

Add accounts

A row in the database is one YubiKey of one user. A user can have several YubiKeys: Radiator finds the right one by the public ID at the start of the OTP, and a label such as primary, slot 1 or spare, slot 2 tells them apart for you (Radiator never reads it). Each command below is for SQLite; add -b pg (or set DB_BACKEND=pg) for PostgreSQL, and leave out sudo there.

One account

add asks for each value you leave out; the private ID, AES key and PIN aren't shown as you type. Press Enter at the label prompt for none:

sudo ./yubikey-db.sh add                              # asks for everything
sudo ./yubikey-db.sh add -u alice -P vvccccbbcdef     # asks for the private ID, key, PIN and label
sudo ./yubikey-db.sh add -u alice -P vvccccbbcdeg -l 'spare, slot 2'
sudo ./yubikey-db.sh add -u kiosk -P vvccccbbcdeh --no-password -l ''

PINs are stored as salted SHA-512 {crypt} hashes. Options -k (AES key) and -w (PIN) also exist, but other users can see them in ps and they stay in your shell history, so let the script ask instead.

If the YubiKey may already be in the database, add --update (see Update and replace).

A test account from a script

yubikey-db-user.example.sh adds or updates one account from variables at the top of a copy of it, which suits test accounts you set up again and again. It sends the values to import --update - through a pipe, so they never appear in ps or a temporary file, shows the account, and then asks you to touch the YubiKey to run verify.

install -m 0700 yubikey-db-user.example.sh ~/yk-user.sh   # your copy will hold an AES key
nano ~/yk-user.sh       # set cred_username, cred_password, cred_publicid, cred_privateid, cred_secret,
                        # cred_label if you want one, and db_backend, db_name and require2factor
                        # if not the defaults
sudo ~/yk-user.sh       # SQLite; for PostgreSQL run it as yourself
shred -u ~/yk-user.sh   # when done

The YubiKey's public ID decides which record is meant; other YubiKeys of the user are left alone. The PIN can't contain a comma, start or end with a space, or be in double quotes, and the label can't contain a comma. An empty cred_label keeps the label the YubiKey already has.

Verify credentials

Check the database: verify

verify asks for a username, PIN and OTP and checks them the way Radiator 4.30 does, without Radiator, so it separates "the database is wrong" from "Radiator is misconfigured":

sudo ./yubikey-db.sh verify
Username: alice
Static password/PIN (Enter for none):
YubiKey OTP (touch the YubiKey): vvccccbbcdefvbvkiggllhvureilrdbnvklrcfivibet
Checking alice with YubiKey vvccccbbcdef in /etc/radiator/db/yubicred.db (Require2Factor on):
  active:           yes
  static password:  matches
  OTP:              decrypts with the stored AES key
  private ID:       matches
  replay check:     passed (OTP counter 3, session 1; stored counter 0, session 0)
Accepted. The OTP's counters were saved, so it cannot be used again.

Each line is one check, so a failure says what to fix: a WRONG PIN, an OTP that doesn't decrypt (the database has a different AES key from the YubiKey), a private ID that doesn't match, or a replayed OTP. It never shows the AES key or private ID. When the YubiKey has a label, a first line label: shows it, so you can see which of the user's YubiKeys was used. An accepted OTP's counters are saved, as Radiator saves them.

  • -u USER gives the username. --no-require2factor matches a Radiator without Require2Factor.
  • Without a terminal, it reads the username (unless -u is given), the PIN and the OTP from standard input, one per line: printf '%s\n' "$pin" "$otp" | ./yubikey-db.sh verify -u alice.
  • It exits with 0 if Radiator would accept the login, 1 if not.

Check the whole path: radpwtst

radpwtst sends a real RADIUS request, so it also tests Radiator's configuration. On the Radiator server, with the secret of <Client 127.0.0.1>:

read -rsp 'PIN: ' PIN; echo; read -rp 'Touch the YubiKey: ' OTP
/opt/radiator/radiator/radpwtst -s 127.0.0.1 -secret local-test-secret -auth_port 1812 -noacct -user alice -password "$PIN:$OTP"
sudo tail -n 1 /var/log/radiator/authentication.log

It prints OK, or Rejected: Request Denied with the reason in the log. Send the same OTP again: it must be rejected with Replay attack detected. Without a YubiKey, make the OTP of a test key with tests/make-otp.sh (see the lab). -auth_port 1812 matters: radpwtst uses port 1645 by default.

Finally, log in through a real RADIUS client: users type their PIN and then touch the YubiKey, in the password field.

Update and replace

add and import refuse a YubiKey that is already in the database. Two options change that:

--update --replace
Same YubiKey (same public ID, private ID and AES key) Username, PIN and active updated; counters and times kept Replaced; counters reset to 0
Reprogrammed YubiKey (same public ID, new private ID or AES key) Replaced; counters reset to 0 Replaced; counters reset to 0
New YubiKey Added Added

Use --update to change a PIN or move a YubiKey to another user: resetting the counters would let OTPs that were already used be accepted again. Use --replace only after programming the same values into a YubiKey again (for example into a replacement YubiKey), because the YubiKey's own counters then start again from 0. Each updated or replaced row is reported.

A lost or stolen YubiKey

  1. Disable it at once: sudo ./yubikey-db.sh disable alice vvccccbbcdef. Logins are checked only against this database, so nothing needs revoking at Yubico.
  2. When it won't come back, delete it: sudo ./yubikey-db.sh delete alice vvccccbbcdef.
  3. Program a new YubiKey and add it.

Backups

export writes every row and field to CSV, with AES keys as 32 hex characters, and import --from-export loads it into either database.

sudo ./yubikey-db.sh export - | gpg -e -r backup@example.com > yubikeys-$(date +%F).csv.gpg
gpg -d yubikeys-2026-10-12.csv.gpg | sudo ./yubikey-db.sh import --from-export --dry-run -
gpg -d yubikeys-2026-10-12.csv.gpg | sudo ./yubikey-db.sh import --from-export --replace -

A restore brings back PINs (as stored), times and counters. With --replace it overwrites existing rows but never moves counters backward, so an old backup can't make used OTPs valid again. export FILE writes a file with mode 0600 instead, and refuses to overwrite one unless you add --force.

You can also back up the database itself: for SQLite, sudo sqlite3 /etc/radiator/db/yubicred.db ".backup '/root/yubicred-backup.db'" takes a consistent copy while Radiator runs; for PostgreSQL, yubikey-backup.sh makes one every day (see Automatic backups). Only such a backup holds the service accounts and groups too. Every backup holds every AES key: keep it encrypted.

Automatic backups

For PostgreSQL, yubikey-backup.sh backs up the whole database every day on each database server: the YubiKeys, the service accounts and the groups.

  • From the server's own PostgreSQL. pg_dump reads the local database, a standby's too, so each server of two or three keeps its own backups.
  • Encrypted for a key that isn't on the servers. The dump goes straight into openssl cms: AES-256-GCM, with a new key for each file, wrapped with RSA-OAEP for a certificate whose private key you keep elsewhere. It is never on disk in clear, and a copy of a backup is of no use without the key.
  • Kept on the server. /var/backups/yubikey-db.cms.0 is the newest: each run moves the others up one (.0 to .1, .1 to .2, ...), and keeps 7 (.0 to .6; KEEP sets how many). They are mode 0640, group adm, so an admin in that group can fetch them.
  • Checked and restored with the same script. check decrypts a backup and reads it back whole, and decrypt writes the dump, on any machine with openssl and pg_restore, and only when the file is whole and unchanged (openssl alone writes out what it decrypted even then). restore, on the primary, says what it would undo and asks first.

1. Make the key pair on an admin's machine, not on a server:

openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:4096 -aes-256-cbc -out backup.key
openssl req -new -x509 -key backup.key -days 7300 -subj "/CN=yubikey backups" -out backup.crt

openssl asks for a passphrase for the key (twice), and for it again to sign the certificate. Keep backup.key in two places, apart from each other and from the servers (two USB drives in two safes, say), and the passphrase on its own (a password manager): whoever has both can read every AES key in every backup. Test that you can decrypt (step 4) before you rely on it. backup.crt isn't secret. It lasts 20 years, but the backups decrypt after it expires too. When you make a new pair, keep the old key as long as you keep backups made for it.

2. On each database server, the certificate, the settings and the timer, and a first backup now:

sudo install -D -m 0644 backup.crt /etc/radiator/backup.crt
sudo install -D -m 0644 /opt/radiator-yubikey/yubikey-backup.example.conf /etc/radiator/backup.conf
sudo systemctl enable --now yubikey-backup.timer
sudo systemctl start yubikey-backup.service
sudo /opt/radiator-yubikey/yubikey-backup.sh status

The timer starts it every day at about 03:00 (the server's time), or at the next boot when the server was off then. status exits with 0 when the newest backup is less than 26 hours old and the last run worked, and 1 otherwise, so monitoring can run it; journalctl -u yubikey-backup has each run.

3. Fetch them to where you keep backups, as a member of the group adm on the server (sudo usermod -aG adm alice):

scp db1.example.com:/var/backups/yubikey-db.cms.0 db1-$(date +%F).cms

  it holds 5 YubiKeys (of 5 users), 4 service accounts, 4 groups

In this example, alice logged in after the backup, bob's YubiKey was disabled and carol's added. The restore replaces every table of the database with the backup's, in one transaction (logins wait for it: a tenth of a second in the test), and so undoes what changed since the backup, which it lists first. Two things stay as they are:

  • Counters that are ahead now, so an OTP used since the backup stays used. A YubiKey deleted since the backup comes back with the backup's counters, and when the database is gone (a new one), every YubiKey has them: an OTP used after the backup could then be used once more, until the YubiKey's next login.
  • The anycast checks' keys (anycast-*), which renew themselves: the checks go on logging in.

A YubiKey or account the list says is enabled again was disabled after the backup: disable it again. It runs only on the primary (on a standby it says so), and takes the backup decrypted already, or encrypted with --key.

It adds what a newer version needs to an existing database and changes nothing else. Version 1.2.1 adds the trigger that stops the same OTP being accepted twice at the same moment (see Database layout). Radiator doesn't need the column, so it keeps working before and after. Version 1.9.0 adds the login_id column to PostgreSQL's table, and changes the trigger to use it: init prints Added the login_id column to the yubikeys table. Version 1.10.0 adds the service-account and group tables (init prints Added the service-account and group tables), and in PostgreSQL the function with which the anycast check renews its key (init prints Added the function anycast_renew, with which the anycast check renews its key); until then, the check logs that it can't renew its key, and works as before. With two database servers or three sites, run init once, against the primary; the standbys get the change by replication.

If your own tools add rows with INSERT INTO yubikeys VALUES (...), without naming the columns, as the old example commands did, they fail once the table has the label column: name the columns, or use add or import.

A database from the old example commands

The example statements that circulated before these scripts stored created as the text current_timestamp, and active as the text true or false. Radiator treats both texts as active, so a YubiKey set to false was never disabled. Fix those rows:

sudo sqlite3 /etc/radiator/db/yubicred.db <<'SQL'
UPDATE yubikeys SET active = 1 WHERE active = 'true';
UPDATE yubikeys SET active = 0 WHERE active = 'false';
UPDATE yubikeys SET created = CURRENT_TIMESTAMP WHERE created = 'current_timestamp';
SQL

They also stored AES keys as hex, private IDs as modhex, and PINs in plain text. Radiator reads hex keys and plain-text PINs, but with CheckSecretId it rejects every login of a YubiKey whose private ID is stored as modhex. export and then import --from-export --replace rewrite every row in the format these scripts use (a modhex private ID becomes hex) and keep the counters; so does a move to PostgreSQL, which also reports each change.

Move from SQLite to PostgreSQL

yubikey-db-migrate.sh copies every user and YubiKey, with their counters and labels, from the SQLite database into an empty PostgreSQL database, in one transaction. It reads a consistent snapshot, so Radiator keeps running on SQLite meanwhile, and commits only after checking every copied row against an independent SHA-256 fingerprint of the snapshot. Rows from the old example commands are normalized and each change is reported (for example, an active of false becomes 0, and the report warns that those YubiKeys could log in before).

It copies only the YubiKeys. Service accounts and groups aren't copied: it warns when the SQLite database has any, and you add them again with yubikey-db.sh -b pg.

The account that runs it must be a member of yubikey_admin and able to read the SQLite file, for example by joining the radiator group (sudo usermod -aG radiator "$USER", then log in again).

  1. Create the PostgreSQL database (see Create the database): sudo -u postgres ./yubikey-db.sh -b pg init-pg --admin "$USER". For a database made by an older version, run ./yubikey-db.sh -b pg init instead, which brings it up to date.
  2. Rehearse: ./yubikey-db-migrate.sh --dry-run /etc/radiator/db/yubicred.db. It does everything, then rolls back.
  3. Copy: ./yubikey-db-migrate.sh /etc/radiator/db/yubicred.db.
  4. Point Radiator at PostgreSQL: ./yubikey-db.sh -b pg config | sudo tee /etc/radiator/conf.d/yubikey.conf >/dev/null, then sudo systemctl restart radiator.
  5. Straight away, catch up with the logins made on SQLite since step 3: ./yubikey-db-migrate.sh --mode sync /etc/radiator/db/yubicred.db. It moves counters forward where SQLite is ahead and adds YubiKeys added meanwhile. It never moves a counter backward, never deletes, and lists (without changing) rows that differ in username, PIN, active, key or label.

Without step 5, an OTP used on SQLite after the copy could be used once more on PostgreSQL. Keep the SQLite file afterwards, unchanged, for a rollback.

To roll back to SQLite, first copy PostgreSQL's counters (and any users added there) into SQLite, then switch:

./yubikey-db.sh -b pg export - | sudo ./yubikey-db.sh import --from-export --replace -
./yubikey-db.sh config | sudo tee /etc/radiator/conf.d/yubikey.conf >/dev/null
sudo systemctl restart radiator

Two database servers

With one PostgreSQL server, logins stop when it does. A second server, kept up to date by PostgreSQL's built-in streaming replication, can take over. tests/radiator/ha.sh runs everything in this section with two database servers and two Radiator servers (see Testing).

How it works

  • One primary, one standby. The primary accepts reads and writes. The standby receives each change from the primary as it happens (in the test, about 6 ms later) and accepts only reads.
  • Every Radiator server lists both servers in one DBSource, with target_session_attrs=read-write. PostgreSQL's client library tries them in order and connects only to the one that accepts writes. So every Radiator server uses the primary, whichever server it lists first, and they all share one set of counters: an OTP used on one Radiator server is rejected on the others.
  • A failover is a promotion. When the primary fails, you promote the standby with one command. It starts accepting writes, and every Radiator server connects to it within 10 seconds, with no change to its configuration. The failed server then comes back as the new standby.

Designs that look simpler but allow replays:

  • Two independent databases, one per Radiator server, or two DBSource lines that point to separate databases: each keeps its own counters, so an OTP used on one is accepted on the other.
  • Two writable servers that replicate to each other (PostgreSQL logical replication both ways): an OTP used on one server is accepted on the other until the change arrives, during normal operation, not only during failures. And when both servers update the same row, the change that arrives last wins, which can move a counter backward.

The replay window

Replication is asynchronous: the primary saves a login's counters and answers Radiator without waiting for the standby. If the primary dies in that moment, the promoted standby doesn't have the newest counters, and those OTPs can be used once more. Only OTPs used in the last fraction of a second before the failure are affected, and only until the user's next login moves the counter past them. In normal operation there is no window, because every Radiator server writes to the same primary. The test shows the window by stopping replication before a failover.

Synchronous replication (synchronous_standby_names) closes the window, but with only two servers every login then stops whenever the standby is down. This guide uses asynchronous replication.

Set up the two servers

Below, the database servers are db1.example.com (192.0.2.11, the first primary) and db2.example.com (192.0.2.12), and the Radiator servers are 192.0.2.21 and 192.0.2.22. The admin opsadmin works on 192.0.2.21.

On both database servers:

  1. Install PostgreSQL and a certificate for that server's own name, made as in PostgreSQL on a separate server (step 1) and signed by the same CA: CN=db1.example.com and subjectAltName=DNS:db1.example.com on db1, and the same with db2 on db2.

  2. Make PostgreSQL listen with TLS and keep recent changes for the standby:

    sudo tee /etc/postgresql/18/main/conf.d/yubikey.conf >/dev/null <<'EOF'
listen_addresses = '*'
ssl = on
ssl_cert_file = '/etc/postgresql/18/main/server.crt'
ssl_key_file = '/etc/postgresql/18/main/server.key'
wal_keep_size = '1GB'
EOF

    wal_keep_size keeps the last 1 GB of changes on the primary, so a standby that was offline for a while can catch up. A login adds at most about 8 KB of changes, so that covers well over 100,000 logins.

  3. Add the same lines on both servers, since either can be the primary, to /etc/postgresql/18/main/pg_hba.conf, above the first line that starts with host:

    hostssl  yubikey      radiator    192.0.2.21/32  scram-sha-256
hostssl  yubikey      radiator    192.0.2.22/32  scram-sha-256
hostssl  yubikey      opsadmin    192.0.2.21/32  scram-sha-256
hostssl  replication  replicator  192.0.2.11/32  scram-sha-256
hostssl  replication  replicator  192.0.2.12/32  scram-sha-256

    Open TCP port 5432 to these addresses in any firewall.

  4. Give the postgres user the CA certificate and the replication password, for when this server is the standby. Choose the replication password now; you set it on the primary in the next part:

    sudo install -d -m 0700 -o postgres -g postgres /var/lib/postgresql/.postgresql
sudo install -m 0644 -o postgres -g postgres ca.crt /var/lib/postgresql/.postgresql/root.crt
sudo touch /var/lib/postgresql/.pgpass
sudo chown postgres:postgres /var/lib/postgresql/.pgpass
sudo chmod 0600 /var/lib/postgresql/.pgpass
echo '*:5432:replication:replicator:REPLICATION-PASSWORD' | sudo tee /var/lib/postgresql/.pgpass >/dev/null

  5. Stop PostgreSQL from starting by itself when the server boots:

    echo manual | sudo tee /etc/postgresql/18/main/start.conf >/dev/null

    Warning

    A primary that restarts by itself after a failover is a second primary, with old counters. A Radiator server that connects to it, for example after a restart, accepts OTPs already used on the new primary. The test shows this. With manual, PostgreSQL starts only when someone runs sudo systemctl start postgresql@18-main: always on a standby, and on the old primary only if no failover happened while it was down.

  6. sudo systemctl restart postgresql@18-main.

On db1, the first primary: create the roles and the database as in PostgreSQL on a separate server (step 4), then the replication role, with the password from step 4 above:

sudo -u postgres ./yubikey-db.sh -b pg init-pg --admin opsadmin --set-password
sudo -u postgres psql -c '\password opsadmin'
sudo -u postgres psql -c 'CREATE ROLE replicator REPLICATION LOGIN'
sudo -u postgres psql -c '\password replicator'

On db2, make it the standby. This replaces db2's database files with a copy of db1's; the old ones are moved aside:

sudo systemctl stop postgresql@18-main
sudo mv /var/lib/postgresql/18/main /var/lib/postgresql/18/main.$(date +%Y%m%d-%H%M%S)
sudo -u postgres pg_basebackup -h db1.example.com -U replicator -D /var/lib/postgresql/18/main \
     -R -X stream -c fast -d 'sslmode=verify-full application_name=db2'
sudo systemctl start postgresql@18-main

-R makes it a standby that follows db1. Check on db1:

sudo -u postgres psql -c 'SELECT application_name, client_addr, state, sync_state, replay_lag FROM pg_stat_replication'
 application_name | client_addr |   state   | sync_state |   replay_lag
------------------+-------------+-----------+------------+-----------------
 db2              | 192.0.2.12  | streaming | async      | 00:00:00.006296
(1 row)

Once it's streaming, delete the moved-aside folder on db2 (sudo rm -rf /var/lib/postgresql/18/main.2*).

Configure Radiator for two servers

On each Radiator server, install the CA certificate as in PostgreSQL on a separate server, list both database servers in PGHOST, and write Radiator's configuration (see Install the configuration):

export PGHOST=db1.example.com,db2.example.com PGUSER=opsadmin PGSSLMODE=verify-full PGSSLROOTCERT=/etc/radiator/pg-ca.crt
./yubikey-db.sh -b pg config | sudo tee /etc/radiator/conf.d/yubikey.conf >/dev/null
sudoedit /etc/radiator/conf.d/yubikey.conf     # put Radiator's password on each DBAuth line
sudo systemctl restart radiator

config writes:

    DBSource     dbi:Pg:dbname=yubikey;host=db1.example.com,db2.example.com;port=5432;sslmode=verify-full;sslrootcert=/etc/radiator/pg-ca.crt;connect_timeout=2;target_session_attrs=read-write
    DBUsername   radiator
    DBAuth       RADIATOR-PASSWORD

    Timeout             2
    ConnectTimeout      5
    FailureBackoffTime  2

with two hooks, ConnectionHook and NoConnectionsHook, and two more clauses, YubiKeyConnect and the group YubiKeyLocal (see below).

  • target_session_attrs=read-write skips the standby, which only accepts reads. A server that doesn't answer is skipped too.
  • connect_timeout=2 gives up on a server that doesn't answer after 2 s. ConnectTimeout (Radiator's limit for the whole connection attempt) must be longer than that times the number of servers.
  • Timeout 2 gives up on a query after 2 s. Radiator's default is 60 s, and Radiator answers nothing else while it waits. The hooks below allow 6 s for 10 s after each new connection.
  • FailureBackoffTime 2: when no server accepts writes, each of Radiator's processes rejects logins without trying for 2 s, then tries again, so logins work again within about 2 s of a promotion. Its default is 600 s, which would leave logins failing for 10 minutes after the standby is promoted. A longer time keeps rejecting after the promotion: with 10 s (and without the hooks below), a planned switchover on three sites rejected logins for about 10 s instead of 2 to 5 s. A shorter one tries more often while there is no primary, and each try waits up to 2 s for each server that doesn't answer, so more rejects take that long: in the lab, with the primary powered off, about 16% of rejects took about 3 s (5% with 10 s), and at a site cut off from the other two, about 14% took about 4 s (3% with 10 s).
  • ConnectionHook and NoConnectionsHook, a few lines of Perl: when no server accepts writes but every listed server answers (the primary refuses connections or is shutting down, the others are standbys), as while you switch over, Radiator holds the login and tries again every 0.5 s, for up to 5 s, instead of rejecting it. When a server doesn't answer at all (timeout expired or No route to host in the log), it doesn't hold: that server may be down for a while, and each held login keeps one of Radiator's processes busy. Radiator builds the query for a login before it runs it, and needs a connection to build it, so a process with no connection must connect first: the group YubiKeyLocal that the Handlers use runs YubiKeyConnect (it connects, holding the login the same way, then lets the login go on), then YubiKeySQL. And for 10 s after each new connection (Radiator reconnects only after a failure), a query may take 6 s instead of 2: a primary just promoted saves a change only once a standby streams from it, 1.5 to 3 s in the lab. The hooks change Radiator's SQLRetries, FailureBackoffTime and Timeout while it runs, as Radiator 4.30's SQL module allows; the tests check them, so run them again with each new Radiator version.
  • YubiKeyConnect also gives each login a random ID, which UpdateQuery passes to the database with the counters. When the primary stops while a login's counters wait for the standby to confirm them, as in a switchover, they are saved, but Radiator only sees its connection drop. It saves them again on the new primary, and the database accepts that second save as the same login's, instead of refusing it as a replay. Without the ID, such a login got no answer: on three sites, with four logins at a time at each site, 6 of 24 planned switchovers left 1 to 3 logins unanswered (10 of 9,180 in all).

For the admins, put both servers in PGHOST in ~/.profile, as above. One ~/.pgpass line with * as the host covers both: *:5432:yubikey:opsadmin:YOUR-PASSWORD. With two servers in PGHOST, the scripts connect to the one that accepts writes. If you also use psql directly, add PGTARGETSESSIONATTRS=read-write to the export line.

Check replication

On the primary, the query above should show the standby as streaming. If it returns no row, the standby isn't receiving changes: look at the standby's log (/var/log/postgresql/postgresql-18-main.log). On the standby:

sudo -u postgres psql -c 'SELECT status, sender_host, latest_end_time FROM pg_stat_wal_receiver'

shows streaming and the primary's name. Check this from your monitoring: a standby that stopped receiving changes is noticed only at the next failover, when it lacks every login since then.

Fail over

When the primary is down:

  1. Make sure it stays down. Power it off, or if you can still reach it, sudo systemctl stop postgresql@18-main. A primary that only hangs, or is cut off from you but not from a Radiator server, can come back and keep accepting logins from a Radiator server still connected to it.

  2. Promote the standby, on the standby:

    sudo pg_ctlcluster 18 main promote
sudo -u postgres psql -Atc 'SELECT pg_is_in_recovery()'     # f: it accepts writes now

  3. Within 10 s every Radiator server uses it. Nothing changes on the Radiator servers or for the admins.

Bring the old primary back as the standby

Don't start PostgreSQL on the old primary as it was. Make it a standby of the new primary, with the commands from Set up the two servers ("On db2, make it the standby"), with the names swapped. For example, on db1 after db2 was promoted:

sudo systemctl stop postgresql@18-main
sudo mv /var/lib/postgresql/18/main /var/lib/postgresql/18/main.$(date +%Y%m%d-%H%M%S)
sudo -u postgres pg_basebackup -h db2.example.com -U replicator -D /var/lib/postgresql/18/main \
     -R -X stream -c fast -d 'sslmode=verify-full application_name=db1'
sudo systemctl start postgresql@18-main

Then check on db2 that db1 is streaming. The copy takes seconds for a database of this size. Radiator servers keep using db2, even those that list db1 first.

Switch over for maintenance

To move the primary to the other server without losing any counter, for example before patching the primary:

  1. On the primary: sudo systemctl stop postgresql@18-main. A clean stop sends every change to the standby first.
  2. On the standby: sudo pg_ctlcluster 18 main promote.
  3. Make the old primary a standby, as above.

Run step 2 within a few seconds of step 1. For 5 s after step 1, Radiator holds logins and accepts them once the standby is promoted; after that it rejects them until step 2, and for up to FailureBackoffTime (2 s) after it.

Automatic failover

The failover in this section is done by a person, who confirms that the primary is down before promoting the standby. A tool that does it automatically must also stop the old primary from coming back as a primary, which needs a third member to tell a dead server from a broken network between two live ones. Three sites does this with Patroni and etcd on three servers. Ubuntu 26.04 also packages pg_auto_failover (with a separate monitor) and repmgr (with a witness), which aren't covered here. Radiator's configuration is the same with any of them, since it follows whichever server accepts writes.

Three sites

With Radiator servers on three sites, each site's server can also hold a copy of the database, and Patroni moves the primary to another site by itself when the primary fails. The example below has three sites, West, East1 and East2, with a 55 ms round trip between West and the East sites and 4 ms between East1 and East2. tests/radiator/geo.sh runs everything in this section on three servers with those delays (see Testing). To set up three sites with partition mode, anycast, groups and TACACS+ from one input file instead of step by step, see Turn-key setup.

How three sites work

  • Each site's server runs the same three services: etcd, PostgreSQL under Patroni, and Radiator.
  • etcd is a small key-value store that the three servers keep identical: a change counts only when two of the three agree. Patroni keeps the name of the primary in it as a lease that the primary renews every 10 s and that expires 30 s after the last renewal.
  • Patroni starts and stops PostgreSQL. The server holding the lease is the primary; the other two stream every change from it. When the lease expires, the most up-to-date standby takes it and is promoted. A server that can't reach either of the others can't renew or take the lease, and its Patroni stops its PostgreSQL before the lease runs out. Nobody promotes anything by hand.
  • Quorum commit (synchronous_mode: quorum): the primary confirms a change only after one of the two standbys has saved it. Every login that Radiator accepted is on two sites, so a failover loses no OTP: the replay window of two servers is closed. East2, 4 ms away, usually confirms first; while East2 is down, West does. And a primary that the standbys no longer follow can't confirm any login.
  • West becomes the primary only as a last resort: its failover_priority is 1, the East sites' is 2. When East2 and West are equally up to date, East2 is promoted.
  • Every Radiator server lists all three servers (PGHOST=east1,east2,west) and uses whichever is the primary, as with two servers. Nothing changes on the Radiator servers when the primary moves.
  • A former primary rejoins by itself. If it has changes that no standby confirmed (counter updates for logins it never answered), Patroni removes them with pg_rewind and makes it a standby.

The cost is distance: every login at West goes to the primary in the East.

Set up the three servers

1. On all three servers, install the packages, in addition to Radiator and its modules from Install on the servers:

sudo apt install postgresql postgresql-client libdbd-pg-perl \
                 etcd-server etcd-client patroni python3-etcd

Patroni needs python3-etcd for etcd, but its package doesn't install it.

2. Make a CA and one certificate per server. etcd, Patroni and PostgreSQL use them for TLS in both directions, so each certificate has the server's name and address, and is valid for servers and clients. On an admin machine:

openssl req -x509 -newkey rsa:3072 -nodes -days 3650 -subj "/CN=YubiKey DB cluster CA" \
        -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign" \
        -keyout ca.key -out ca.crt
mkcert() {   # mkcert NAME ADDRESS
    openssl req -newkey rsa:3072 -nodes -subj "/CN=$1" \
            -addext "subjectAltName=DNS:$1,IP:$2" \
            -addext "keyUsage=critical,digitalSignature,keyEncipherment" \
            -addext "extendedKeyUsage=serverAuth,clientAuth" -keyout "${1%%.*}.key" -out "${1%%.*}.csr"
    openssl x509 -req -in "${1%%.*}.csr" -CA ca.crt -CAkey ca.key -CAcreateserial -days 825 \
            -copy_extensions copy -out "${1%%.*}.crt"
}
mkcert east1.example.com 192.0.2.31
mkcert east2.example.com 198.51.100.32
mkcert west.example.com 203.0.113.33

Copy ca.crt and each server's own .crt and .key to it, and keep ca.key offline. Any certificate this CA signs can change the cluster's state in etcd, so use this CA only for these three servers. Patroni refuses a CA certificate without the keyUsage line (Python 3.13 and later).

What the settings do:

When a site is cut off

  • West cut off from both East sites: East1 keeps the lease and East2 confirms its commits; nothing changes at the East sites. West can't reach a primary: its logins are rejected. Its PostgreSQL stays a standby, so there is no second primary. When the network is back, it catches up by itself.
  • East1 (the primary) cut off from both others: its Patroni can't renew the lease and stops PostgreSQL within about 10 s. A login on East1 in that moment gets no answer, because no standby confirms its commit. When the lease expires, East2 is promoted, and logins work again everywhere except at East1. When the network is back, East1 is rewound and rejoins as a standby; move the primary back to it.
  • The link between East1 and East2 fails, both still reaching West: East1 keeps the lease (etcd still has a majority through West), and West confirms its commits, so logins at East1 take a WAN round trip longer. East2 can't reach the primary: its logins are rejected until the link is back.

Partition mode

With three sites, a site that can reach no other site can't reach a primary either, so it rejects every login until the network is back. Partition mode lets that site log users in from a copy of the keys on its own server while it is cut off, and copies the counters back to the primary when the network returns. It is optional: yubikey-partition.sh runs it, on each of the three servers. tests/radiator/geo.sh tests it after everything else (see Testing).

How partition mode works

  • A copy of the keys on each server. Every 5 minutes, yubikey-partition.sh updates a SQLite copy of the yubikeys table, /var/lib/yubikey-partition/keys.db, from the server's own PostgreSQL (a standby or the primary), through the local socket. New, changed, disabled and deleted YubiKeys follow; counters only move forward.
  • Cut off: Radiator uses the copy. Every 5 s, the script checks whether the other two servers answer, on PostgreSQL's port or Patroni's. When neither has for 3 checks in a row, the server is cut off. The script updates the copy once more: a standby that is cut off still answers reads, with every change up to the cut. Then it points Radiator's /etc/radiator/conf.d/yubikey.conf, which is a link, at yubikey-partition.conf (Radiator's clause for the copy) instead of yubikey-cluster.conf, and restarts Radiator. Logins at that site work again, and their counters are saved in the copy.
  • If PostgreSQL doesn't answer at that moment, the last copy. When the primary is cut off, Patroni stops its PostgreSQL, which then refuses connections for about a minute before it starts again as a standby. If partition mode begins during that minute, the copy is the one from the last 5-minute update, and it is updated as soon as PostgreSQL answers. (In the test, East1's PostgreSQL still answered when partition mode began.)
  • Back: the counters go to the primary. When another server answers and the primary can be reached, twice in a row, the script copies to the primary the counters that moved forward in the copy (only forward, with Radiator's own database login), points the link back at the cluster, restarts Radiator, and copies once more, for logins in between.
  • Only when no other site answers. A site that still reaches another site doesn't use its copy: East2 while only its link to East1 is down, or every site while Patroni replaces a primary. They reject, as before.

The risks you accept with partition mode:

  • While a site is cut off, an OTP that a user typed at another site can be used once more at the cut-off site, which can't know about it. On a former primary whose PostgreSQL didn't answer when partition mode began, so can an OTP typed anywhere in the last 5 minutes before the cut, until it answers. And an OTP used at the cut-off site can be used once more at another site, until the network is back and its counters have reached the primary.
  • A user disabled, a PIN changed or a YubiKey deleted elsewhere while a site is cut off still works at that site until the network is back.
  • Each server keeps every AES key in a second place, the copy.

Anycast

With anycast, every Radiator server has the same IPv4 and IPv6 address on its loopback interface, and FRR advertises it to the site's router with BGP. The network devices are given that one address as their RADIUS server (and TACACS+ server) and reach their own site's server. When a server can't log anyone in, it stops advertising the address, and its site's devices reach another site.

yubikey-anycast.sh decides: every 5 s it logs in to the local Radiator, with a key of its own that works like a YubiKey's, and, with TACACS+, over TACACS+ too. The example below adds anycast to the three sites of the previous section. tests/radiator/geo.sh runs it with an FRR router in front of the three servers (see Testing).

How anycast works

  • One address for all servers: 192.0.2.153 and 2001:db8:153::153 below, in none of your networks. Each server's FRR advertises them to its site's router, as /32 and /128, while they are on the server's lo. Each router prefers its own server, so devices use their own site.
  • The check puts them on lo and takes them off. Every 5 s it logs in to Radiator through 127.0.0.1 as anycast- and the server's name (for example anycast-west), with a PIN and an OTP made from its own key, and checks that Radiator listens on the anycast addresses. A login succeeds only if Radiator works, reaches the primary, and the primary saved the OTP's counter. After 2 good checks in a row the addresses go on lo, and FRR advertises them. After 3 failed checks they come off, and FRR withdraws them.
  • With TACACS+, a check is two logins. With TACACS_KEY in its settings, each check also logs in over TACACS+, at the same time, as the service account svc.anycast- and the server's name, with a password of its own; asks for the session's authorization, as a device does; and checks that Radiator listens on TCP port 49 on the anycast addresses. The check fails if either login fails, so a server whose TACACS+ is broken is withdrawn like one whose RADIUS is. The TACACS+ login goes through the same password and group checks as anyone's, and uses no OTPs.
  • The check renews its key every year. Like a YubiKey's, its OTPs have counters that only go up, so a key runs out: after about 485 days at one check every 5 s. Every 365 days, after a good check, the running check gives its key a new private ID and AES key, in the database and in its key file, and its counters start again. It writes with Radiator's own login, through a function in the database that can change only the keys of anycast-* users. Never in partition mode.
  • Nothing is advertised unless the check says so. The addresses aren't in the server's network configuration, and FRR's configuration never changes: FRR advertises what is on lo, even after it restarts. A server that reboots, or whose check stops or crashes, advertises nothing until its check has passed twice again. Stopping the check (systemctl stop yubikey-anycast) withdraws the addresses at once, which is how to take a server out for maintenance.
  • BFD tells the router that a server is gone within a second, instead of after BGP's hold time (minutes, by default).
  • Radiator listens on the anycast addresses even while they aren't on lo. Two kernel settings (ip_nonlocal_bind) allow that, so a Radiator that starts while its server is withdrawn answers as soon as the addresses are back. Its BindAddress lists them, so the reply to a request sent to an anycast address comes from that address: network devices drop a reply from any other address.
  • The check's users work nowhere else. Radiator accepts anycast-* users (and svc.anycast-* service accounts) only from 127.0.0.1, and doesn't write their logins to the authentication log.

The check withdraws a server whenever its logins fail, whatever the reason. While no server can log anyone in, for example while Patroni replaces a primary that lost power, every server withdraws after 3 checks, and devices get no answer instead of a reject until a server's check passes again. A network device that falls back to its local accounts when no RADIUS server answers will do so during that time. With partition mode, a site that reaches no other site logs users in from its copy, so its check passes and it keeps advertising.

Before you start

  • The anycast addresses: one IPv4 and one IPv6 address for RADIUS, the same on every server, in none of your networks: 192.0.2.153 and 2001:db8:153::153 below.
  • Each server's own IPv6 address, for its BGP session over IPv6: 2001:db8:31::31 (east1), 2001:db8:32::32 (east2) and 2001:db8:33::33 (west) below. Their routers are 192.0.2.1 and 2001:db8:31::1, 198.51.100.1 and 2001:db8:32::1, and 203.0.113.1 and 2001:db8:33::1.
  • The cluster stays on IPv4. The three servers' names in /etc/hosts have IPv4 addresses only; etcd, Patroni and PostgreSQL keep using those. If a name also resolves to an IPv6 address, PostgreSQL may refuse the connection (no pg_hba.conf entry for host "2001:...").
  • AS numbers: the servers use one private AS, 65053 below, the same on all three; the routers use yours, 64500 below.
  • Firewall: between each server and its router, TCP 179 (BGP) and UDP 3784 (BFD). From the devices to the anycast addresses, UDP 1812, and TCP 49 for TACACS+.
  • The devices get the anycast addresses as their RADIUS server (and TACACS+ server). Each server still needs a <Client> for each device, with the same secret (and TACACS+ key) on every server.

Groups and TACACS+

With radiator-groups.example.conf instead of radiator.example.conf, Radiator also takes logins over TACACS+ (TCP port 49), and checks every login, RADIUS or TACACS+, against groups in the same database: which accounts may log in to which devices, at which TACACS+ privilege level, with which commands, and with which RADIUS reply attributes. It also takes service accounts: accounts that log in with a password instead of a YubiKey, for scripts and tools, named svc.NAME.

How groups work

  • A device group is the Identifier of the devices' <Client> clauses in Radiator, for example core for the core switches. Several devices or subnets can share one. A <Client DEFAULT> clause takes every device that isn't listed, in a device group of its own.
  • A group holds accounts: YubiKey users and service accounts.
  • Access lets a group log in to the devices of a device group (or to every device, *), at a TACACS+ privilege level from 0 to 15, with RADIUS reply attributes for RADIUS logins, and, if you want, TACACS+ command rules.
  • At each login, after the YubiKey or password check, Radiator looks for the most privileged of the account's groups that may use the device's group (a named device group before *). If there is none, the login is rejected. An account counts only while it can log in: it has an active YubiKey, or it is an active service account.
  • Over TACACS+, the device then asks Radiator to authorize the session (exec), and, if it is set up to, each command. Radiator answers with the group's privilege level and command rules. Each of these requests asks the database again, so a change applies within 2 seconds, even to sessions already open: taking a group's access away, or disabling an account, stops its commands.
  • Command rules are tried in order, and the first that matches decides. A command no rule matches is denied. A group with no rules on a device group may run every command there.
  • enable on a device is a second login, which takes a new OTP. With the privilege level from the group, users don't need it.
  • The groups are in the database: a change applies on every server at once, with no Radiator restart. The devices are in Radiator's configuration: adding one takes sudo systemctl restart radiator, which also closes the TACACS+ connections that are open (devices open new ones).

Radiator 4.30's TACACS+ has no TLS. Its packets are protected only by the device's key (RFC 8907's MD5-based obfuscation): give each device a long random key, and keep TACACS+ on your management network.

Service accounts

A service account logs in with a password, at least 12 characters, stored as a {crypt} SHA-512 hash like the PINs. Its name is svc. followed by letters, digits and . _ @ + -, which is how Radiator tells it from a YubiKey user. Like any account, it may log in only where its groups allow.

sudo ./yubikey-db.sh service add svc.backup -l 'nightly config backup'   # asks for the password twice
sudo ./yubikey-db.sh service add svc.monitor --generate                  # makes one, and shows it once
sudo ./yubikey-db.sh group add backup
sudo ./yubikey-db.sh member add backup svc.backup
sudo ./yubikey-db.sh access set backup core 15
sudo ./yubikey-db.sh rule add backup core 'permit service=shell cmd=show cmd-arg=running-config'
sudo ./yubikey-db.sh rule add backup core 'permit service=shell cmd=copy'

Command rules

A rule is permit, permitreplace or deny, then one pattern for each argument of the TACACS+ request, in order, as Radiator's AuthorizeGroup takes them. Each pattern is a Perl regular expression that must match the whole argument. A device asks about show running-config as service=shell cmd=show cmd-arg=running-config cmd-arg=<cr>; a rule with fewer patterns than the request has arguments ignores the rest.

Rule Allows or denies
permit service=shell cmd=show Every show command
permit service=shell cmd=show cmd-arg=running-config Only show running-config
deny service=shell cmd=reload reload
permit service=shell Every command
deny .* Everything 
sudo ./yubikey-db.sh rule add netadmins core 'deny service=shell cmd=reload'
sudo ./yubikey-db.sh rule add netadmins core 'permit service=shell'
sudo ./yubikey-db.sh rule list netadmins core
sudo ./yubikey-db.sh rule delete netadmins core 10
sudo ./yubikey-db.sh rule add netadmins core 'permit service=shell cmd=show' --seq 5   # before the first

Rules are numbered 10, 20, 30 and so on; --seq puts one in between. Once a group has rules on a device group, a command none of them matches is denied, so the netadmins example above ends with permit service=shell. A rule may not contain a double quote, or an octal escape such as \101.

Turn-key setup

yubikey-turnkey does all of Three sites, Partition mode, Anycast and Groups and TACACS+ for you, from one input file: you describe the three servers, their routers, the anycast addresses, the devices and the groups in site.toml, and it makes a folder for each server, with a setup.sh that installs and configures everything on it, and the sheets to hand to whoever runs the routers and the devices. tests/radiator/turnkey.sh runs it on three fresh servers (see Testing).

How the turn-key setup works

  • One input file, with no secrets in it. site.toml lists the three servers (the usual primary first, and the one far from the others as the last resort), each one's router or two, the anycast addresses, the admins and their subnets, the devices with their device groups, and the groups to start with. site.example.toml, in the package, is an example with everything it assumes in its comments.
  • Every secret is made once. The passwords, the RADIUS secrets and TACACS+ keys, the anycast checks' keys, and the cluster's CA and certificates are made the first time, in secrets.toml next to site.toml (mode 0600), and taken from there on every later run: the same input always gives the same output. Keep secrets.toml, and back it up.
  • A folder per server, made by the tool. In out/ next to site.toml: east1/, east2/ and west/, each with setup.sh, the server's settings (server.env, secrets.env), every file it installs (files/, listed with their modes in files.list), and on the first server the database's first contents (db/). Next to them, runbook.md (the order to do things in), routers.md, devices.md, admin/ (the files for the admins' machines), and with [backup], secrets.toml.cms.
  • setup.sh does the steps of the sections above, in order: the packages (PostgreSQL, Patroni, etcd and FRR from Ubuntu; Radiator and radiator-yubikey from the packages next to it), /etc/hosts and the kernel settings, the cluster's TLS files, etcd, Patroni, the database, Radiator (radiator-groups.example.conf with the server's addresses and devices), partition mode, FRR and the anycast check, the backups, and the firewall. It ends with a report: the cluster, the anycast check, the BGP sessions.
  • The three run at the same time. etcd starts only when two servers run it; the first server's Patroni creates the cluster, which the other two copy; the first server makes the database, and the others wait for it. Each says what it waits for.
  • It is safe to run again. Each step changes only what differs from the folder, and restarts a service only when its files changed. If setup.sh stops, fix the cause and run it again: it goes on where it stopped. It never removes an etcd cluster or a PostgreSQL cluster with databases that it didn't make; --reset starts a server over.
  • One command says whether a server works: setup.sh --status checks its services, the cluster, the anycast check, partition mode, BGP, the backups, the firewall, the certificates, the disk and the clock, without changing anything, and sums it up in its first line, for you and for monitoring.
  • Backups, encrypted for a key that isn't on the servers (with [backup] in site.toml, as in the example): each server makes the automatic backups, and yubikey-turnkey writes secrets.toml encrypted for the same certificate, which each server keeps too (see Turn-key backups).
  • The database's first contents, once. The first server loads the three anycast checks' keys and TACACS+ service accounts, the group anycast-check, and the groups in site.toml, each only if it isn't there yet. After that, change the groups with yubikey-db.sh: a later run doesn't undo it, and a key the check has renewed stays.
  • The devices are in the folders. Radiator's <Client> clauses come from site.toml. To add a device, add it there, run yubikey-turnkey again, copy the folders and run setup.sh on each server, which restarts Radiator (and so closes the TACACS+ connections that are open).
  • The firewall (when on, as by default): setup.sh turns ufw off and loads iptables rules for the whole server, kept by iptables-persistent (with the nft backend). Only these come in: from the devices to the anycast addresses, RADIUS and TACACS+ (from anyone, with the catch-all client); between the three servers, etcd, PostgreSQL and Patroni; from the admin subnets, SSH, PostgreSQL and Patroni's REST API; from the server's routers, BGP and BFD; ICMP, and replies to the server's own connections. It refuses to load them while an SSH connection to the server comes from outside the admin subnets.

Turn-key backups

With [backup] in site.toml, setup.sh installs the certificate and /etc/radiator/backup.conf, starts the daily timer and makes the first backup on each server: the automatic backups, with keep of them (7 by default: /var/backups/yubikey-db.cms.0 to .6).

[backup]
certificate = "backup.crt"  # next to site.toml; its private key is kept elsewhere
keep = 7

  • Fetch them and check one now and then as in steps 3 and 4 of Automatic backups. setup.sh --status warns when the newest is more than 26 hours old, the last one failed, or the timer is off.

  • Restore one on the primary (east1, unless it failed over), as in step 5. The anycast checks' keys stay, so all three servers go on advertising.

  • After losing the whole cluster: set up servers with the same names and addresses, copy the folders and run setup.sh on all three, as on new servers, which makes the database anew with the anycast checks and the groups of site.toml, and then restore the last backup on east1. tests/radiator/turnkey.sh does this after --reset on all three.

  • secrets.toml, encrypted: yubikey-turnkey writes out/secrets.toml.cms, secrets.toml encrypted for the same certificate, and each server keeps a copy as /var/backups/yubikey-turnkey-secrets.toml.cms. It is made again only when secrets.toml or the certificate changes, so the output stays the same. If you lose secrets.toml, fetch a copy and decrypt it:

    ./yubikey-backup.sh decrypt --key backup.key yubikey-turnkey-secrets.toml.cms secrets.toml

  • A new key pair: replace backup.crt, run yubikey-turnkey, copy the folders and run setup.sh on each server, which makes a backup for the new certificate at once. Keep the old key while you keep backups made for it.

  • Without [backup], the servers make no backups (yubikey-turnkey says so), and setup.sh turns the timer off where it was on; the backups already made stay.

Change a turn-key setup

  • Devices, groups to start with, admin subnets, partition mode, the firewall: change site.toml, run yubikey-turnkey again (it prints what it wrote, and --check what it would write), copy the folders again (scp -r out/east1/. root@east1.example.com:/root/turnkey/), and run setup.sh on each server. A device that is gone from site.toml keeps its secret in secrets.toml, in case it comes back.
  • A device's existing secret or key: put it in secrets.toml (8 to 128 printable characters, without spaces, quotes, \, #, %, ` or |), and run yubikey-turnkey. Remove a value to have a new one made.
  • New certificates for the servers (they last 825 days; the tool warns 60 days before): yubikey-turnkey --renew-certs site.toml, then copy the folders and run setup.sh on each server, one at a time.
  • A server's name or address can't change this way once the cluster runs: etcd and Patroni keep them. That, and replacing a server, are not covered yet.
  • Start over: sudo /root/turnkey/setup.sh --reset NAME (NAME: the server's host name) stops the services and removes the server's etcd member, PostgreSQL cluster, anycast key and setup.sh's state. Run it on all three, then setup.sh on all three again: the database is made anew, without the YubiKeys, which a backup can bring back (the backups in /var/backups stay).

Security

  • The database holds every user's AES key. Anyone who can read it can copy the YubiKeys. The SQLite file is mode 0640, readable by root and radiator only. In PostgreSQL, only yubikey_admin members and the radiator role can read the table.
  • Exports, CSV files and backups hold every AES key in clear text. Encrypt them (export - | gpg -e ...), keep CSV files at mode 0600, never commit them or attach them to tickets, and delete them with shred -u. The script warns about a CSV file that all users can read.
  • A filled-in copy of yubikey-db-user.example.sh holds an AES key. Keep it at mode 0700, outside the repository, and shred -u it when done.
  • Replace the package's sample radiator.conf (it accepts every login from 127.0.0.1) and give every RADIUS client its own long random secret.
  • Trace 4 writes every user's AES key and PIN hash to Radiator's log (the AuthSQLYUBIKEY read: lines). Use it only on a test server with test keys, and delete the log afterwards. radiator.example.conf uses Trace 3.
  • Keep Require2Factor unless you mean OTP-only logins for everyone: without it, the PIN is optional.
  • /etc/radiator/conf.d/yubikey.conf holds Radiator's database password for a remote PostgreSQL: mode 0640, owner root:radiator. ~/.pgpass must be mode 0600.
  • Remote PostgreSQL: hostssl lines for single addresses in pg_hba.conf, scram-sha-256 passwords, and sslmode=verify-full on the clients, so a server without your CA's certificate is refused.
  • A standby holds every AES key too, and the replicator role can copy the whole database: protect both database servers alike, and keep ~postgres/.pgpass at mode 0600.
  • Three sites: each server holds every AES key, so protect all three alike. Any certificate signed by the cluster's CA can change which server is the primary, through etcd: use that CA only for these three servers and keep ca.key offline. /etc/patroni/18-main.yml holds the replication, rewind and REST API passwords: mode 0640, owner root:postgres. Patroni's REST API answers health checks without a password but takes commands, such as a switchover, only with it; open port 8008 only to the three servers and your monitoring.
  • Partition mode: the copy, /var/lib/yubikey-partition/keys.db, holds every AES key, like the database: mode 0640, owned by radiator. yubikey-cluster.conf holds Radiator's database password (mode 0640, owner root:radiator); partition mode uses that login to copy counters back. See the risks of using the copy.
  • Anycast: /var/lib/yubikey-anycast/key holds a working login, the check's PIN and AES key, and /var/lib/yubikey-anycast/tacacs the password of its TACACS+ service account: mode 0600, root only. Radiator accepts the check's users (anycast-*, and svc.anycast-* in radiator-groups.example.conf) only from 127.0.0.1, because of the <Handler> clauses for them; keep those before the ones for everyone else. /etc/radiator/anycast.conf holds the secret and TACACS+ key of <Client 127.0.0.1>: mode 0600. Radiator's PostgreSQL role may run the function anycast_renew, which gives the key of an anycast-* user a new private ID and AES key (and nothing else); since that role can already read every AES key, it lets it do little more than log in as the check from a Radiator server. Each router accepts only the two anycast routes from its server. If your routers require BGP passwords, FRR sets them with neighbor ADDRESS password (the test doesn't use them).
  • Groups and TACACS+: the files in /etc/radiator/clients.d hold every device's RADIUS secret and TACACS+ key: mode 0640, owner root:radiator. Radiator 4.30's TACACS+ has no TLS, only the key's obfuscation: long random keys, and TACACS+ only on your management network. Service accounts' passwords are salted SHA-512 {crypt} hashes; in PostgreSQL, Radiator's role can read only those hashes (with the names and active) and the view access_replies, and change nothing in the group tables. Keep the two Authorize-Only Handlers of radiator-groups.example.conf before the others: the first works around Radiator answering a refused TACACS+ authorization with a packet devices take for an error (which some then treat as allowed), the second refuses Authorize-Only from RADIUS clients, which would otherwise get an account's reply attributes without a password. A RADIUS client can't send YubiKey-Via, which marks TACACS+ requests (its number can't be carried in a RADIUS packet).
  • Turn-key setup: secrets.toml holds every password and key of the deployment and the cluster's CA key, and out/ copies of them: keep both where only you can read them (the tool makes them mode 0600 and 0700), back up secrets.toml, and don't send devices.md (every device's secret and key) further than needed. Each server's folder holds only what that server needs; the first server's also holds the anycast checks' keys of all three, to load them. setup.sh keeps a copy of the server's settings and secrets in /etc/yubikey-turnkey (root only). The admins' passwords reach the servers only as SCRAM verifiers. Its firewall leaves outgoing traffic open.
  • Automatic backups hold every AES key, encrypted for the backups' certificate: only its private key decrypts them, so keep it off the servers, in two places, with its passphrase apart from it. The servers keep them readable by the group adm, for the admins to fetch. A decrypted dump holds every AES key in clear: shred -u it after a restore. restore brings back what the backup had, also YubiKeys or accounts disabled since: it lists them (enabled again). secrets.toml.cms is encrypted for the same certificate.
  • The scripts pass AES keys and PINs to sqlite3 and psql through their input, never on a command line, and quote every value. PINs are stored as salted SHA-512 {crypt} hashes (-H clear stores plain text, if something else must read it).

Start with verify for the user: if it accepts the login and Radiator doesn't, the problem is in Radiator's configuration or the network.

Database layout

The table is yubikeys, one row per YubiKey:

Column SQLite PostgreSQL Contents
username varchar(255) varchar(255) The login name; indexed, not unique
password varchar(64) text PIN: {crypt}$6$..., plain text, or empty
active boolean smallint, 0 or 1 1 allows logins; Radiator treats only 0 or empty as disabled
created datetime timestamptz When the row was added (UTC)
accessed datetime timestamptz Last successful login; empty until then
tokenId varchar(60) varchar(60) Public ID (modhex); unique
userId varchar(60) varchar(60) Private ID (hex); primary key
secret varchar(60) varchar(60) AES key, base64 (or hex)
counter, low, high int integer The replay counters (low is the session counter; Radiator sets high to 0)
label varchar(255) varchar(255) Describes the YubiKey, for people; empty for none. Radiator doesn't read it. Added in 1.8.0.
login_id varchar(64) PostgreSQL only: the ID of the Radiator login that last saved the counters, kept by the trigger; empty after a save by the scripts. Added in 1.9.0.

PostgreSQL roles: yubikey_admin owns the database and table; its members manage users. radiator can SELECT username, password, active, tokenId, userId, secret and the counters, and UPDATE only accessed and the counters; it can't read the labels, nor read or write login_id.

In both databases, the trigger yubikeys_counters_forward refuses an UPDATE of counter or low that doesn't move them forward, with the error counter violation: ... already used this OTP or a later one. To reset a YubiKey's counters on purpose, replace its row (add --replace).

In PostgreSQL, the trigger lets one kind of such save through: the same login saving the same counters again. Radiator does that when the answer to its first save was lost, as when the primary stops while the save waits for the standby (the save was made, but the connection dropped). Radiator's UpdateQuery names the login, with the random ID YubiKeyConnect gives it (set_config('yubikey.login_id', ...), for that save only), and the trigger keeps the ID in login_id. A save that names no login, from the scripts or from a clause written by config before 1.9.0, empties login_id. Two logins with the same OTP have different IDs, so the second is still refused.

In PostgreSQL, the function anycast_renew(public ID, private ID, new private ID, new AES key) (added in 1.10.0) is how the anycast check renews its key with Radiator's login. It runs with the rights of its owner, yubikey_admin, and radiator may run it. It replaces only the row of an anycast-* user with that public ID and private ID, by a row with the new private ID and AES key (stored as hex or base64, as the row's was), the same username, PIN, public ID and label, and counters at 0. It answers true when the row has the new key, also when called again after the answer was lost, and false when there is no such row.

Table Columns Contents
service_accounts username (key), password, active, created, changed, label Service accounts: svc.NAME, a {crypt} hash, 1 or 0, when added and when the password was last set
user_groups name (key), label Groups
group_members user_group, username Who is in each group: YubiKey users and service accounts, by username
group_access user_group, device_group, priv_lvl, radius_reply The device groups each group may use (*: every one), at privilege level 0 to 15, with RADIUS reply attributes

The view access_replies has one row for each active account, group it is in and device group that group may use, with the RADIUS reply and the TACACS+ rules Radiator returns (OSC-Authorize-Group attributes: the privilege level first, then the rules, or permit service=shell when there are none). Export format

How Radiator 4.30 checks a login

Read from Radiator 4.30's source (Radius/AuthYUBIKEYGENERIC.pm) and confirmed with real logins (tests/radiator/run.sh). verify follows the same steps.

  1. The login is PIN: (optional), a 12-character public ID, and the 32-character token; PIN may also come right before the OTP without a colon. Any other public ID length is never found.
  2. The row is found by username and public ID (%0 and %3 are quoted).
  3. The YubiKey is rejected if active is 0 or empty. Any other value, including the texts true and false, and NULL, counts as active.
  4. The PIN is checked if one was typed, or always with Require2Factor. An empty stored PIN never matches. {crypt}, {SSHA}, $6$ and other common formats, and plain text, are accepted.
  5. A secret of 32 hex characters is read as hex, anything else as base64. The token must decrypt with a valid CRC.
  6. With CheckSecretId, the token's private ID must equal userId exactly (lowercase hex).
  7. The top bit of the usage counter (set when the OTP was triggered from a keyboard key) is ignored. The OTP is a replay unless its counter is above the stored counter, or equal with a session counter above low. A NULL counter skips this check.
  8. UpdateQuery saves the counter, the session counter (low), 0 (high) and the time. If the save fails, Radiator ignores the request (no answer) with Database update failed. That is what happens to the second of two logins with the same OTP at the same moment: both pass the check in step 7 before either saves, and the database refuses the second save. When a save fails because the connection dropped, Radiator connects again and repeats the same save; in PostgreSQL the trigger accepts the repeat if the first save was made.

Testing

tests/run-tests.sh runs the scripts through 48 scenarios against throwaway SQLite and PostgreSQL databases and compares each transcript (commands, output, exit codes, and the final table) with tests/expected/, where the scripts' version shows as <VERSION>. The two anycast scenarios run yubikey-anycast.sh against a stand-in RADIUS server, which checks each request the way Radiator does, a stand-in TACACS+ server, and stand-ins for ip and ss; pg_anycast renews the check's key in the test's PostgreSQL, with Radiator's login. pg_partition runs yubikey-partition.sh with the test's PostgreSQL as both the local database and the primary, a stand-in for systemctl, and a peer that is a port that listens or doesn't. groups and pg_groups also run Radiator's GroupAccess query from config on the database (on PostgreSQL, as Radiator's role). install runs install.sh with stand-ins for apt-get, dpkg-query and Radiator, installed in each of the ways it recognizes. turnkey runs yubikey-turnkey on site.example.toml with fixed secrets (tests/turnkey/example-secrets.toml) and shows everything it writes; turnkey_errors its checks of the input, and turnkey_secrets the secrets it makes, and changed by hand. backup runs yubikey-backup.sh's settings, status and decrypt (of whole, changed and cut files), and pg_backup its backups, checks and restores in the test's PostgreSQL, with the test key pair in tests/turnkey/ (passphrase test-only).
