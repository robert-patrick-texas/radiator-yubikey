Overview

Use yubikey-db.sh to:

  • create the database and its yubikeys table
  • add users one at a time, or in bulk from a CSV file
  • list, enable, disable, and delete users
  • print a matching Radiator configuration block

yubikey-db.sh

The management script. Run it on, or next to, the Radiator server.

users.example.csv

A sample bulk-import file that contains test values only.

This guide

Setup, day-to-day use, and troubleshooting.

How offline YubiKey authentication works

Each time someone touches a YubiKey, it types a 44-character one-time password. The first 12 characters are the key's public ID. The remaining 32 are encrypted with an AES key that is stored on the YubiKey.

Radiator's <AuthBy SQLYUBIKEY> module:

  1. looks up the user and public ID in the SQLite database
  2. decrypts the OTP with the AES key stored for that YubiKey
  3. compares the YubiKey's use counters with the saved values, so a captured OTP can't be replayed, and then saves the new counters
Key point

Nothing leaves the Radiator server. The catch is that Radiator must know each YubiKey's AES key. Yubico keeps the factory-programmed key secret, so every YubiKey must be reprogrammed with a key you generate, and that key must be loaded into this database.

Quick start

# 1. Create the database so the Radiator service account can write to it
sudo ./yubikey-db.sh init --owner radiator:radiator

# 2. Load users from a CSV file (check the file first, then import it)
sudo ./yubikey-db.sh import --dry-run users.csv
sudo ./yubikey-db.sh import users.csv

# 3. Print the Radiator config block and paste it into radius.cfg
./yubikey-db.sh config

# 4. Confirm the users are loaded
sudo ./yubikey-db.sh list

The database is created at /etc/radiator/db/yubicred.db unless you set a different path with -d (see Global options).

Step 1: Program the YubiKeys

Do this once for each YubiKey, on a trusted workstation. The command overwrites OTP slot 1 or 2, which is the slot that types an OTP when the key is touched briefly.

Warning

Slot 1's factory configuration can't be restored. After you reprogram it, the key no longer works with services that check OTPs through YubiCloud.

ykman otp yubico 2 --serial-public-id --generate-private-id --generate-key

ykman shows three values. Record them for this user:

ykman outputCSV columnFormat
Public IDpublic_id12 modhex characters (only cbdefghijklnrtuv)
Private IDprivate_id12 hex characters
Secret keyaes_key32 hex characters
Do not

Do not add --upload. That option sends the key to Yubico.

To use a public ID that you choose instead of one based on the serial number, replace --serial-public-id with --public-id <modhex>.

Step 2: Create the database

sudo ./yubikey-db.sh init --owner radiator:radiator
  • init is safe to run again. It doesn't change an existing table or its data.
  • --owner should be the account that the Radiator service runs as. Radiator writes to the database after every login to save the counters that block replayed OTPs. SQLite also creates a temporary journal file next to the database, so Radiator needs write access to the folder as well as the file. If Radiator runs as root, you can leave out --owner.
  • New files are created with mode 0640 and new folders with 0750.

Step 3: Load users

Option A: Bulk import from a CSV file

Create a CSV file with these columns:

username,public_id,private_id,aes_key,password,active
alice,vvccccbbcdef,4a6f8e2d1c3b,6b1f0a9d2c7e4f3a8b5d0c1e9f2a7b6d,1234,1
bob,vvccccbbcdeg,9e8d7c6b5a41,0f1e2d3c4b5a69788796a5b4c3d2e1f0,,yes
ColumnRequiredNotes
usernameYesThe RADIUS login name. Allowed characters: letters, digits, and . _ @ + -
public_idYesYubiKey public ID in modhex (usually 12 characters)
private_idYes12 hex characters. 12 modhex characters are also accepted and converted to hex.
aes_keyYes32 hex characters. Spaces and colons are removed.
passwordNoStatic password or PIN for two-factor logins. Leave it empty if users log in with the OTP only.
activeNo1/0, true/false, or yes/no. The default is 1.

CSV rules:

  • The header row is optional.
  • Blank lines and lines that start with # are skipped.
  • Windows (CRLF) line endings are accepted.
  • Spaces around fields and double quotes around a field are removed.
  • Fields can't contain commas, including passwords.
  • One user can have several YubiKeys: add one row per key.

Import steps:

chmod 600 users.csv                                # the file contains secret keys
sudo ./yubikey-db.sh import --dry-run users.csv    # check every row; makes no changes
sudo ./yubikey-db.sh import users.csv              # load the users
shred -u users.csv                                 # securely delete the file when done

How the import works:

  • Every row is checked first: field formats, plus duplicate public IDs or private IDs within the file. Problems are reported with their line numbers.
  • If any row is invalid, nothing is imported. Fix the file, or add --skip-invalid to load only the valid rows.
  • Valid rows are loaded in one transaction. If any row fails (for example, because the YubiKey is already in the database), none are loaded.
  • Add --replace to overwrite YubiKeys that are already in the database, for example after reprogramming them.

See users.example.csv for a working example.

Option B: Add one user

If you run add with no values, it asks for each one. The private ID, AES key, and password aren't shown as you type:

sudo ./yubikey-db.sh add

You can also pass the values as options:

sudo ./yubikey-db.sh add -u alice -P vvccccbbcdef        # asks for the private ID, key, and password
sudo ./yubikey-db.sh add -u svc.backup -P vvccccbbcdeh --no-password
Caution

Values passed with -k (AES key) and -w (password) can be seen by other users in ps and are saved in your shell history. Let the script ask for them, or use a CSV file.

Step 4: Configure Radiator

Print a config block that already contains your database path:

./yubikey-db.sh config
# or, for a database in another location:
./yubikey-db.sh -d /srv/radius/yubi.db config

Paste the output into radius.cfg and reference it from your <Handler> with AuthBy YubiKeyLocal. The block it prints:

<AuthBy SQLYUBIKEY>
    Identifier   YubiKeyLocal
    DBSource     dbi:SQLite:dbname=/etc/radiator/db/yubicred.db
    DBUsername
    DBAuth
    AuthSelect   select secret, active, userId, counter, low, high, password from yubikeys where username=%0 and tokenId=%3
    UpdateQuery  update yubikeys set accessed=datetime(%5,'unixepoch'), counter=%0, low=%1, high=%2 where username=%3 and tokenId=%7
    Require2Factor
    CheckSecretId
</AuthBy>

What the settings do:

SettingPurpose
AuthSelectFinds a row by both the username and the YubiKey's public ID. This lets one user have several YubiKeys and stops one user's YubiKey from working for another user.
UpdateQuerySaves the counters after each login. It takes the time from Radiator's %5 value (the time in seconds) because SQLite doesn't support current_timestamp().
Require2FactorMakes users enter their static password, a colon, and then the OTP, for example 1234:vvccccbbcdef…. Remove this line if users log in with the OTP only.
CheckSecretIdAlso checks the private ID inside the OTP against the database.

Restart Radiator after you change its configuration.

Step 5: Test a login

Use Radiator's radpwtst tool. Touch the YubiKey where the OTP goes:

# Two-factor (Require2Factor set)
radpwtst -s 127.0.0.1 -secret <shared-secret> -noacct \
         -user alice -password '1234:<touch YubiKey here>'

# OTP only
radpwtst -s 127.0.0.1 -secret <shared-secret> -noacct \
         -user alice -password '<touch YubiKey here>'

Then check that the counters were updated:

sudo ./yubikey-db.sh list alice      # "accessed" and "counter" should now be filled in

Enter the same OTP a second time. It must be rejected; that's the replay protection working.

Before the first rollout

Test with Trace 4 in radius.cfg and read the SQL statements Radiator logs. See Values to confirm on your first deployment.

Database layout

The table is yubikeys. There is one row per YubiKey.

ColumnContents
usernameRADIUS login name. Indexed. Not unique, because one user can have several YubiKeys.
passwordStatic password or PIN: {crypt}$6$..., plain text, or empty
active1 = allowed, 0 = disabled. Radiator rejects any value other than 1.
createdWhen the row was added (UTC)
accessedTime of the last successful login (UTC). Empty until the first login.
tokenIdYubiKey public ID in modhex. Unique.
userIdYubiKey private ID in hex. Unique. This is the primary key.
secretAES key, in base64 by default
counter, low, highCounters that Radiator uses to block replayed OTPs

--replace resets a YubiKey's counters to 0. Only use it for a YubiKey that has just been reprogrammed.

Security notes

  • The database holds every user's AES key. Anyone who can read the file can copy those YubiKeys. Keep the file at 0640 or stricter, readable only by the Radiator account and root. Include it in encrypted backups only.
  • CSV files hold the same secrets. Set them to chmod 600, don't commit them to Git or attach them to tickets, and delete them with shred -u after importing. The script warns you if a CSV file is readable by all users.
  • AES keys and passwords are sent to sqlite3 through its input, not on its command line, so ps doesn't show them. The script checks the format of every value and quotes it safely.
  • Passwords are stored as salted SHA-512 {crypt} hashes by default. Only use -H clear if something else needs to read the plain-text password.
  • To revoke a lost YubiKey, use disable or delete straight away. Logins are checked against this database only, so there's nothing to revoke in a cloud service.

Troubleshooting

SymptomCause and fix
sqlite3 not foundInstall sqlite3, or set SQLITE3=/path/to/sqlite3.
no write access to ... (run with sudo?)Run the script with sudo, or as the account that owns the database.
UNIQUE constraint failed: yubikeys.tokenId (or userId)That YubiKey is already in the database. Add --replace if it was reprogrammed.
import failed and was rolled backNo rows were loaded. Fix the cause shown above the message and run the import again.
nothing imported; fix the rows aboveOne or more CSV rows are invalid. Fix them, or add --skip-invalid.
All logins are rejected and active shows trueThe row was created with the old example commands. See Upgrading old databases.
Logins fail and Radiator logs attempt to write a readonly databaseRadiator can't write to the file or its folder. Run init --owner <radiator-user> again.
Logins fail and Radiator logs a bad OTP or decryption failureThe secret column is in the wrong format. See Values to confirm.
Logins fail and Radiator logs a CheckSecretId mismatchThe private ID is wrong, or is stored in a different format. Check it against the ykman output.
The first OTP works but the next ones failUpdateQuery isn't saving counters. Check the folder permissions and the UpdateQuery line.
database is lockedRadiator is writing at that moment. The script waits up to 5 seconds, so run it again.

Values to confirm on your first deployment

These settings come from the Radiator 4.x reference manual. Confirm them on one test server with Trace 4 before you load users in bulk:

  1. AES key format. The manual says the secret column holds the key in base64, but it also says the default setup assumes hex. The script stores base64. If logins fail with decryption errors, rebuild the test database with -e hex and test again.
  2. Quoting of %3 and %7. The sample config assumes Radiator quotes the public ID, as it does the username in %0. In the trace log, check that the SQL shows tokenId='vvcc...'.
  3. Two-factor login format. Check the password:OTP format with radpwtst before you tell users how to log in.

After these work on one server, use the same settings everywhere.

Upgrading a database built with the old example commands

The original example commands created rows that Radiator can't use:

  • "current_timestamp" in double quotes stored the literal text current_timestamp in created, not the date and time.
  • active="true" stored the text true, but Radiator only accepts 1.

To fix the existing rows:

sudo sqlite3 /etc/radiator/db/yubicred.db <<'SQL'
UPDATE yubikeys SET active = 1 WHERE active = 'true';
UPDATE yubikeys SET active = 0 WHERE active = 'false';
UPDATE yubikeys SET created = CURRENT_TIMESTAMP WHERE created = 'current_timestamp';
SQL

The old commands also stored the AES key in hex, the private ID in modhex, and passwords in plain text. The cleanest fix is to export your source data to the CSV format above and re-import it with --replace, so that every row matches what this script creates.
